# Migration 0.1.0 to 0.1.1

This migration applies through `playbooks/upgrade.md` to a workspace whose
validated manifest records release `v0.1.0`. It updates installed engineering
guidance without changing the manifest schema or adapter contracts.

## Scope and affected paths

The changed portable source is `core/instructions/engineering.md`. It covers
readability, minimal diffs, necessary complexity, proper fixes and workaround
disclosure, comments, repository conventions, and end-to-end validation.

Use the manifest and recorded source ownership to identify outputs containing
that installed module, normally the shared `AGENTS.md`. Do not infer ownership
or module selection from a filename. If the mapping is ambiguous, stop and
resolve it before planning writes. If engineering guidance is not selected,
preserve instruction files and record the filtered step as a warning; do not
claim the skipped module migration was applied.

The distribution's release checklist in its root `AGENTS.md` and bootstrap
playbook changes govern the starter source only. Do not copy them into an
adopter's project instructions. Existing client configuration, skills, roles,
project facts, and Claude's `@AGENTS.md` shim need no changes for this release.

## Plan and apply

1. Follow the upgrade playbook's manifest, release-range, hash, and local-change
   checks. Classify each affected output and present the complete plan for
   approval before changing generated workspace files.
2. Preserve unmanaged and user-owned files. For `merge` outputs, propose a
   semantic update of only the engineering guidance, preserving project rules
   and unrelated sections; resolve conflicting local instructions explicitly.
   For `replace-if-unmodified` outputs, replace only clean managed files and
   preserve all other selected content. Missing or modified replacement outputs
   remain conflicts under the upgrade playbook.
3. After approval, back up affected outputs and the manifest and create the
   durable run record. Embed the selected engineering policy in the retained
   shared instructions rather than linking to the removable starter checkout.
   Apply only the approved changes; do not install unselected modules or clients.

## Validation and manifest

Review the generated diff against the selected source and verify all policy
areas above are present, local conventions and unrelated sections are preserved,
and no source-checkout dependency was introduced. Check the selected clients'
instruction entrypoints and required imports against their adapter contracts.
Verify output hashes and validate the manifest against
`core/manifest/manifest.schema.json`. Record exact checks and their evidence
under `core/validation/ACCEPTANCE.md`; optional live client checks may be skipped
with an explanation, never reported as passed.

Only after required validation succeeds, update the manifest release to
`v0.1.1`, the source release of modules actually updated, and affected output
hashes. Record `0.1.0-to-0.1.1` when applied, retaining filtered-step warnings
and skipped or blocked checks. Leave schema and adapter versions unchanged.

## Rollback

On conflict, write failure, or required validation failure, stop and follow the
upgrade playbook's rollback procedure. Restore affected outputs and the previous
manifest from the pre-upgrade copy when required or approved, verify the original
hashes, and preserve the run record and failure report. Never restore over newly
modified or unmanaged content without resolving that conflict. Do not leave a
manifest claiming `v0.1.1` when the upgrade is incomplete.
