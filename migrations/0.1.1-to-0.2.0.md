# Migration 0.1.1 to 0.2.0

Apply through the target release's `playbooks/upgrade.md` to a workspace whose
validated manifest records `v0.1.1`. This migration adds upgrade discovery after
starter removal and moves the manifest to schema version 2. Adapter contracts
and optional engineering policy are unchanged.

## Scope and provenance

Affected paths are `.agent-template/manifest.yaml` and the managed shared
`AGENTS.md` entrypoint identified by the ownership record. Do not infer ownership
from the filename or install unselected client outputs. Existing Claude imports
continue to use the shared entrypoint without changes.

The target schema accepts version 1 manifests for this migration. Verify the
source clone URL and target `v0.2.0` tag/commit before planning changes. If the
legacy repository value is ambiguous, obtain evidence or human clarification;
do not guess the host or the original source commit. Record the missing original
commit as a provenance limitation in the upgrade evidence.

## Plan and apply

Follow the upgrade playbook's ownership, hash, local-change, and approval gates.
Include backups of the manifest and affected instructions in the plan. Propose
adding the Harness updates section from `playbooks/bootstrap.md` to the managed
shared entrypoint, preserving project-specific instructions and unrelated
content. Point it to the retained workspace manifest, never the removable clone.

Apply the recorded output policy: review semantic changes for `merge`, replace
only clean managed outputs for `replace-if-unmodified`, and preserve unmanaged
or user-owned files. Missing outputs, unresolved local conflicts, or an absent
managed entrypoint require an explicit plan decision; do not silently adopt
files. If the entrypoint cannot be updated, report the remaining human action
and do not claim that upgrade discovery or starter removal is ready.

After approval, create the backups and durable run record, then apply only the
planned instruction changes. Do not create `UPDATE.md` or another upgrade-guide
file. Preserve all other selected modules, client configuration, and project
context.

## Validation and manifest

Verify that the retained shared entrypoint leads to the manifest, that the
verified origin and target tag/commit locate `playbooks/upgrade.md`, and that
all required instruction paths remain usable without the starter checkout.
Review the diff for preserved project rules, ownership, and local changes.
Report checks under `core/validation/ACCEPTANCE.md`; optional live client checks
may be skipped with reasons. Unavailable required source retrieval is blocked.

Only after required checks pass, atomically write the manifest with
`schema-version: 2`, the verified credential-free clone URL in
`template.repository`, `template.release: v0.2.0`, and the full target commit ID
in `template.commit`. Update affected output hashes and record
`0.1.1-to-0.2.0` in applied migrations, retaining warnings and validation results.
Keep unrelated module source releases and adapter versions unchanged. Validate
the resulting manifest against `core/manifest/manifest.schema.json`.

## Rollback

On failure, stop and follow the upgrade playbook's rollback procedure. Restore
affected instructions and the previous manifest from the pre-upgrade copy when
required or approved, verifying original hashes. Preserve newly modified and
unmanaged files, retain the failure/run record, and do not leave a manifest
claiming the new release when the upgrade is incomplete.
