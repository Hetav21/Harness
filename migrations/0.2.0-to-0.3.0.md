# Migration 0.2.0 to 0.3.0

Apply through the target release's `playbooks/upgrade.md` to a workspace whose
validated manifest records `v0.2.0`. This migration upgrades the manifest to
schema version 3 with required source-module attribution, introduces mandatory
workspace path validation checks, advances the Codex adapter to version 2,
preserves role template contract constraints, and supports unspecialized
workspace routing.

## Scope and affected paths

The updated distribution components include:
- `core/manifest/manifest.schema.json`: Advances schema version to 3, requiring
  a non-empty `source-modules` array on all generated output records (exempting
  `user-owned` outputs). Backward compatibility is retained for reading legacy
  version 1 and version 2 manifests.
- `core/manifest/PATH-CHECKS.md`: Codifies filesystem containment, path traversal
  rejection, symlink escape prevention, and duplicate destination checks required
  before any workspace writes.
- `adapters/codex/adapter.yaml`: Advances adapter contract to version 2, adopting
  native Codex configuration and role schema conventions.
- `adapters/antigravity/templates/.agents/agents/role/agent.md.template`: Adds
  required role frontmatter (`name` and `description`).
- Role templates across all adapters: Ensure explicit denied scope and capability
  requirements are preserved in accordance with `core/roles/ROLE-CONTRACT.md`.
- `catalog/skills/workspace-router/SKILL.md`: Permits verified workspace routing
  to proceed even when no specialized skill exists for a repository or task.

## Plan and apply

1. Follow the upgrade playbook's manifest, release-range, hash, and local-change
   checks. Apply the [workspace path checks](../core/manifest/PATH-CHECKS.md) to
   the full proposed plan, including the retained manifest, project-context,
   backup, and run-record destinations.
2. For each managed generated output, attribute its contributing source files
   relative to the template repository and assign them to `source-modules`.
   Obtain human verification for ambiguous mappings rather than inferring them
   from filenames. User-owned files do not require source modules.
3. If Codex is an installed client, plan the translation of Codex configuration
   and role definitions to adapter version 2 specifications. For Antigravity,
   ensure role templates include valid frontmatter.
4. For `merge` outputs such as shared `AGENTS.md` and router skills, propose
   semantic updates that incorporate the new routing and path check rules while
   preserving project-specific facts and local customizations.
5. Present the complete plan and obtain explicit human approval before altering
   any generated workspace files. After approval, create pre-upgrade backups and
   a durable run record before applying approved replacements and merges.

## Validation and manifest

Verify that all output paths satisfy the workspace path checks. Check that role
templates retain denied scopes and capability requirements, that the Antigravity
role includes frontmatter, and that any Codex configuration complies with the
adapter version 2 schema. Validate the upgraded manifest against
`core/manifest/manifest.schema.json`.

After all required checks pass, atomically update the manifest with:
- `schema-version: 3`
- `template.repository` (verified credential-free clone URL)
- `template.release: v0.3.0`
- `template.commit` (full verified target commit ID)
- Updated output records with accurate `source-modules` and content hashes
- Installed Codex `adapter-version: 2` (if installed)
- `0.2.0-to-0.3.0` recorded in `applied-migrations`

Retain all existing warnings, skips, and blocks.

## Rollback

On conflict, write failure, or validation failure, immediately stop and follow
the upgrade playbook rollback process. Restore affected outputs and the manifest
from the pre-upgrade backup, re-verify original content hashes, and preserve the
failure report and run record. Do not leave a workspace manifest claiming
`v0.3.0` or schema version 3 when the upgrade is incomplete.
